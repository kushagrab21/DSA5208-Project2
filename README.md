# DSA5208 Project 2: Singapore rainfall, 2017–2024, with Apache Spark

Kushagra Bhatnagar (A0351591A) · Pratyush Sinha (A0352482A)

We use the eight annual files of data.gov.sg's "Historical Rainfall across Singapore" (collection 2279): 5-minute
rain readings per station, 2017–2024, 48.5 million rows in all. They are processed with the Spark DataFrame API, and
the models are built and evaluated with Spark MLlib.

- **Task 1** describes how rainfall varies within a year and across years.
- **Task 2** estimates P(a station's rain in the next 30 minutes > θ) from the station, the prediction time and θ.
- The data are also checked against the official Meteorological Service Singapore (MSS) daily records.

The report is [`report/DSA5208_Project2_Report.pdf`](report/DSA5208_Project2_Report.pdf). Every number in it is
generated by `src/report_macros.py` from the pipeline's outputs.

## Contents

| Path | What it is |
|---|---|
| `src/` | the pipeline (one script per stage, listed below) |
| `checks/` | checks that print a verdict and refuse to continue on a failure (see "Checks") |
| `config/eval_plan.json`, `config/eval_plan.lock` | the Task 2 evaluation plan, frozen by SHA-256 before any model was fitted |
| `config/test_run.json` | the record of the single evaluation on 2024 |
| `models/model_A`, `models/model_B` | **the trained models** (Spark ML `PipelineModel`s) |
| `outputs/` | every table the stages produce (CSV/JSON); the report and figures are built from these |
| `figures/` | the report's figures (PNG) |
| `report/` | LaTeX source, `generated/` (all numbers and tables), and the PDF |
| `runs/<run id>/env.json` | the computing environment captured by each Spark job |
| `cloud/` | the Google Cloud Dataproc run (`dataproc_run.sh`) |
| `data/` | raw CSVs (not included), Parquet, MSS daily files |

```bash
brew install openjdk@17 python@3.11

```

The raw data go in `data/raw/rainfall_<year>.csv` for 2017–2024. They come from data.gov.sg collection 2279 (one
dataset per year, about 7.5 GB in total). Spark runs in local mode with `local[10]` and a 10 GB driver; to change these,
set `P2_MASTER` and `P2_DRIVER_MEM`.

## Run the pipeline, in order

The runtimes below are for a 10-core Apple M5 with 16 GB of memory, from `runs/*/env.json`.

| # | Command | What it does | Time |
|---|---|---|---|
| 1 | `python src/ingest.py` | CSV → Parquet with an explicit schema, partitioned by year; nothing filtered | 23 s |
| 2 | `python checks/ingest_check.py` | rows, stations and span per year; `MISSING YEARS: 0`; Parquet rows = CSV lines | 19 s |
| 3 | `python src/clean.py` | cleaning rules, ledger, station table | 10 min |
| 4 | `python checks/clean_ledger.py` | `CLEAN rule=… removed=n of N`; refuses if any row is unaccounted for | 14 s |
| 5 | `python checks/coverage_check.py` | stations, station-days and share of slots per year | 4 s |
| 6 | `python checks/stuck_runs.py` | runs of identical positive readings (stuck gauges) | 11 s |
| 7 | `python src/task1.py` | Task 1 aggregation (Spark) → `outputs/task1/` | 63 s |
| 8 | `python src/plot_task1.py` | Task 1 figures | seconds |
| 9 | `python src/mss_fetch.py probe` then `python src/mss_fetch.py fetch` | official MSS daily files, sequential and cached (about 5,000 requests, about 1 h) | ~1 h |
| 10 | `python src/mss_validate.py` then `python src/plot_mss.py` | agreement with MSS and the cost of gaps | 61 s |
| 11 | `python src/task2_features.py` | per (station, slot) past-rain features and the 30-minute future total | 2 min |
| 12 | `python checks/eval_plan.py verify` | the plan must still match its frozen hash | instant |
| 13 | `python src/task2_sample.py` | training and validation samples and the baselines, from the frozen plan | 42 s |
| 14 | `python src/task2_train.py` | fit Models A and B (MLlib), choose on 2023, save `models/` | about 15 min |
| 15 | `python src/task2_test.py --dry-run` | run the test path on 2023 and require it to reproduce validation | about 2 min |
| 16 | `python src/task2_test.py` | **the single 2024 evaluation**; refuses if already run or if the plan changed | 83 s |
| 17 | `python src/task2_coefficients.py` then `python src/plot_task2.py` | Model B coefficients; Task 2 figures | about 1 min |
| 18 | `python src/report_macros.py` then `cd report && tectonic DSA5208_Project2_Report.tex` | numbers and tables, then the PDF (Tectonic 0.17) | seconds |
| 19 | `python checks/requirements_check.py` | E1–E14 mapped, no hand-typed numbers, authors, AI declaration | instant |

Step 16 can only run once. To repeat it, a person must delete `config/test_run.json` deliberately, and that deletion
should be reported.

## Use the trained models

```bash
source env.sh
python src/predict.py --station S24 --time 2024-06-01T15:00 --threshold 0.5 2 10
```

This prints, for each threshold, P(rain at the station in the next 30 minutes > θ) from Model A (strict: station, time
and θ only) and Model B (nowcast: the same interface, but it also looks up the station's and its neighbours' readings
up to the given time). Times are Singapore time and are moved back to the latest 5-minute slot. If the station has no
reading at that time, B falls back to A.

The models are ordinary Spark ML pipelines and can be loaded directly:

```python
from pyspark.ml import PipelineModel
model_b = PipelineModel.load("models/model_B")    # input columns: see src/task2_train.py (build_pipeline)
```

## Checks

Each check prints a verdict. The enforced ones stop the pipeline (exit status 1) on a failure:

- **Enforced:** `ingest_check`, `clean_ledger`, `eval_plan` (the freeze, the guard against test-year rows, and the
  single test run), `requirements_check`.
- **Print only:** `coverage_check`, `stuck_runs`.

`python checks/qualify.py` gives each enforced check a deliberately broken input and requires it to refuse:

- a missing year;
- one row unaccounted for in the ledger;
- a random split;
- an edited frozen plan;
- a second test run;
- a 2024 row in a fitting table;
- a report with a hand-typed number, an unmapped requirement or an undefined generated value;
- a Dataproc output set with one count that differs from the local run (`checks/cloud_parity.py`).

The log is `outputs/qualification/qualification.log`.

## Run on Google Cloud Dataproc

`cloud/dataproc_run.sh` runs stages 1–14 on a Dataproc cluster. It **creates billed resources**, so read its header
first. It needs an authenticated `gcloud` and `P2_GCP_PROJECT`.

```bash
export P2_GCP_PROJECT=<project id>
cloud/dataproc_run.sh plan       # prints the shape, the order and a cost estimate; creates nothing
cloud/dataproc_run.sh bucket     # bucket + code (+ the raw CSVs, unless P2_FETCH_ON_CLUSTER=1)
cloud/dataproc_run.sh cluster    # image 3.0-debian13 (Spark 4.1, as in Lecture 6)
cloud/dataproc_run.sh rawfetch   # optional: download the CSVs from data.gov.sg on the cluster instead of uploading
cloud/dataproc_run.sh jobs       # envcheck, then every stage in order (cloud/run_on_cluster.py per stage)
cloud/dataproc_run.sh fetch      # outputs, env.json files and models → cloud_run/
cloud/dataproc_run.sh delete     # delete the cluster
python checks/cloud_parity.py    # cloud outputs vs local: counts must match exactly, metrics closely
python src/report_macros.py && (cd report && tectonic DSA5208_Project2_Report.tex)   # report now covers both
```

**The run we made.** The project's quota is 12 vCPUs in total. We therefore used:
- 1 n2-standard-4 master and 2 n2-standard-4 workers, each with an 80 GB pd-balanced disk;
- image 3.0-debian13, zone asia-southeast1-b;
- the CSVs downloaded on the cluster (`rawfetch`);
- Spark properties `spark.executor.instances=2`, `spark.executor.cores=3`, `spark.executor.memory=8g`,
  `spark.driver.memory=8g`, `spark.sql.shuffle.partitions=48`.

The report's Dataproc subsection is generated from `cloud_run/cluster.json` and `cloud_run/runs/*/env.json`; it is not
typed. The cloud run stops after Task 2 validation; the 2024 test and every reported model are the local ones.

**Workaround specific to our network.** On the machine we used, `gcloud storage` and `gsutil` hung, and request bodies
over about 32 KB failed. Our wrapper therefore:
- uploaded files through the Cloud Storage JSON API in 24 KB parts, joined with the compose API;
- submitted jobs with `--async`;
- polled the Dataproc API for job state.

On a normal network, `cloud/dataproc_run.sh` as written does the same job.
